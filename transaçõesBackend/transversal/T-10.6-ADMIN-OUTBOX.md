# T-10.6 — Admin Outbox: Gerenciar Eventos DEAD

> **Status:** ✅ Implementado — AdminOutboxController com list, detalhe, retry e descarte

---

## Por que existe

Durante a demo ou em produção, eventos podem chegar ao estado `DEAD` (8 tentativas falhadas). O Admin Outbox permite:
- Visualizar o payload e o erro da última tentativa
- Resetar o evento para `PENDING` e retentar (útil se o SMTP estava fora)
- Descartar eventos que não podem ser processados

## API

### GET /admin/outbox?status=DEAD&page=0 — Listar eventos
```json
{
  "content": [
    {
      "id": "uuid",
      "eventType": "iam.password_reset_requested",
      "aggregateType": "Usuario",
      "aggregateId": "uuid",
      "status": "DEAD",
      "attemptCount": 8,
      "lastError": "Connection refused to SMTP server",
      "nextAttemptAt": "2025-08-01T10:00:00Z",
      "createdAt": "2025-08-01T09:00:00Z"
    }
  ],
  "totalElements": 3
}
```

### GET /admin/outbox/dead — Atalho para eventos DEAD
Equivalente a `GET /admin/outbox?status=DEAD`.

### GET /admin/outbox/{id} — Detalhe com payload completo
```json
{
  "id": "uuid",
  "eventType": "iam.password_reset_requested",
  "payload": { "email": "joao@ufpr.br", "nome": "João", "token": "..." },
  "status": "DEAD",
  "attemptCount": 8,
  "lastError": "..."
}
```

### POST /admin/outbox/{id}/retry — Reenviar evento DEAD
```json
// Response 200
{ "mensagem": "Evento reagendado para reprocessamento.", "status": "PENDING" }
```
- Verifica `status == "DEAD"`
- Reseta: `status = "PENDING"`, `attemptCount = 0`, `lastError = null`, `nextAttemptAt = now()`
- O dispatcher vai processá-lo no próximo ciclo (≤ 5s)

### DELETE /admin/outbox/{id} — Descartar evento
```json
// Response 204 No Content
```
- Remove o evento do banco (apenas se `status == "DEAD"`)
- Irreversível — usar com cuidado

## FGAC

Todos os endpoints requerem `system.admin` — apenas ADMIN tem essa authority.
