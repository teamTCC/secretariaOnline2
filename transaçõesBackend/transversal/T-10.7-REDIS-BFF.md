# T-10.7 — Redis: Session Store + Cache BFF + Force-Logout

> **Status:** ✅ Redis 7-alpine — session store (fail-closed) + cache BFF (TTL 60 s) + force-logout + read ports Clean Architecture (7 módulos)

---

## Por que Redis foi adicionado

Dois papéis distintos, um único container — agora com session store como mecanismo primário de autenticação:

### 1. Session Store — mecanismo principal de autenticação (v2)

Cada access token JWT carrega um claim `sid` (session ID). O backend grava `auth:session:<sid>` no Redis no momento do login (e a cada refresh). O `JwtAuthenticationFilter` verifica a existência dessa chave em **todo request autenticado**.

**Logout = deletar a chave Redis** — o token é invalidado instantaneamente, independente do TTL do JWT. Não há acúmulo de blacklist.

**Política fail-closed**: se o Redis estiver indisponível, `sessionExists()` lança exceção → o filtro captura → authentication não é definida → request recebe 401. Disponibilidade é sacrificada em favor de segurança.

### 2. Cache BFF Dashboard

- **SLA FCP < 1,5s**: cada endpoint `/bff/dashboard/*` faz 4–6 queries ao Postgres. Com cache, a resposta típica cai de ~150ms para ~5ms.
- **Degradação controlada**: quando `_degraded = true`, o resultado **não é cacheado** — o próximo request tenta Postgres de novo.

### 3. Force-Logout (marcador por usuário)

Complementa o session store para cobrir tokens emitidos antes de um evento de segurança (ex: roubo de refresh token detectado, reset de senha). Grava `auth:force-logout:user:<uuid>` com o timestamp do evento.

## Esquema de Chaves Redis

| Prefixo | Valor | TTL | Responsável | Política |
|---------|-------|-----|-------------|----------|
| `auth:session:<sid>` | userId (UUID string) | accessTTL + 60 s | `LoginUseCase` / `RefreshTokenUseCase` | fail-closed |
| `auth:force-logout:user:<uuid>` | Epoch-ms do evento | accessTTL | `RefreshTokenUseCase` / `ResetPasswordUseCase` | fail-closed (check) |
| `auth:revoked:jti:<jti>` | `"1"` | TTL restante do token | `AuthController.logout()` (legacy) | fail-closed (check) |
| `bff-dashboard::<key>` | JSON serializado | 60 s | `Dashboard*Query` cache-aside | fail-open (cache) |

## Fluxo de Autenticação — Session Store

### Login
```
LoginUseCase.execute()
  → gera sid = UUID.randomUUID().toString()
  → jwtTokenService.issueAccessToken(usuario, sid)  ← JWT com claim "sid"
  → tokenRevocationPort.createSession(sid, userId, ttl=accessTTL+60s)
  → Redis: SET auth:session:<sid> <userId> EX <ttl>
```

### Verificação por request (filtro)
```
JwtAuthenticationFilter.doFilterInternal()
  → extrai token do cookie access_token (ou Bearer header)
  → jwtTokenService.verify(token) → payload
  → sid = payload["sid"]
  → if (sid != null):
      sessionExists(sid)  ← Redis: EXISTS auth:session:<sid>
      → NÃO existe → rejeita (session expirou ou logout foi feito)
      → Redis indisponível → lança exceção → request não autenticado (fail-closed)
  → isUserForcedLogout(userId, issuedAt)  ← cobre tokens pré-force-logout
```

### Logout
```
AuthController.logout()
  → extrai sid do payload do access token atual
  → tokenRevocationPort.deleteSession(sid)
  → Redis: DEL auth:session:<sid>   ← token inválido imediatamente
  → refreshTokenRepository.revokeAllForUser(userId)
  → clear cookies (MaxAge=0)
```

### Refresh (nova sessão a cada rotação)
```
RefreshTokenUseCase.execute()
  → valida refresh token (DB)
  → gera novo sid = UUID.randomUUID().toString()
  → tokenRevocationPort.createSession(newSid, userId, ttl)
  → jwtTokenService.issueAccessToken(usuario, newSid)
  ← token antigo com sid anterior expira no TTL natural (≤ 15 min)
```

## Políticas de Falha

| Operação | Redis indisponível | Razão |
|----------|--------------------|-------|
| `createSession()` | **lança exceção** (login falha) | Não pode emitir token sem sessão registrada |
| `deleteSession()` | log WARN, continua | Cookie é limpo; sessão expira via TTL |
| `sessionExists()` | **lança exceção** (request negado) | Fail-closed: segurança > disponibilidade |
| `forceLogoutUser()` | log WARN, continua | Best-effort; session TTL cobre a janela |
| `isUserForcedLogout()` | **lança exceção** (request negado) | Fail-closed |
| `isRevoked(jti)` | **lança exceção** (request negado) | Fail-closed |
| `revokeAccessToken()` | log WARN, continua | Legacy/best-effort |
| Cache BFF (`put/get`) | silencioso (Spring) | Disponibilidade > consistência para cache |

## Redis no docker-compose (Produção local)

```yaml
redis:
  image: redis:7-alpine
  command: >
    redis-server
    --appendonly yes
    --appendfsync everysec
    --maxmemory 256mb
    --maxmemory-policy noeviction
  volumes:
    - redis_data:/data
```

**`noeviction`**: Redis recusa novos writes quando a memória está cheia, em vez de evictar chaves de autenticação silenciosamente.

**AOF (`appendonly yes`)**: sessions e force-logout markers sobrevivem a reinícios do container.

## Arquitetura BFF — Read Ports (Clean Architecture)

### Por que ports são necessários

Sem ports, as queries do BFF importariam `RequestJpaRepository`, `EventAttendanceJpaRepository` etc. diretamente — ou seja, a camada `infrastructure` de um módulo seria visível fora do módulo. Isso viola a regra de dependência do Hexagonal Architecture e impede ArchUnit de verificar as fronteiras.

### Solução implementada

Cada bounded context expõe um contrato de leitura (`Read Port`) em sua camada `application/ports/out/`. O BFF injeta a interface, nunca o repositório JPA:

```
BFF (DashboardXxxQuery)
  │  injeta interface
  ▼
solicitacoes/application/ports/out/SolicitacaoDashboardPort   ← contrato
  │  implementa
  ▼
solicitacoes/infrastructure/persistence/SolicitacaoDashboardAdapter  ← JPA aqui
  │
  ▼
RequestJpaRepository                                           ← detalhe de infraestrutura
```

### Regra ArchUnit equivalente (a acrescentar futuramente)

```kotlin
noClasses()
    .that().resideInAPackage("..bff..")
    .should().dependOnClassesThat()
    .resideInAPackage("..modules.*.infrastructure.persistence..")
```

Com os ports em vigor, essa regra passaria sem exceções.

### DTOs dos ports

Cada port define seus próprios DTOs (data classes) no mesmo arquivo. Exemplos:
- `RequestCardDto(id, tipo, estado, prazoEm, createdAt)` — em `SolicitacaoDashboardPort.kt`
- `EventCardDto(id, titulo, estado, chCreditadas, inicioEm, fimEm)` — em `PresencaDashboardPort.kt`
- `CertificateCardDto(id, hashSha256, issuedAt)` — em `PresencaDashboardPort.kt`
- `UsuarioBasicoDto(nome, email, grr)` — em `IamDashboardPort.kt`
- `ComunicadoCardDto(id, idCommunication, deliveredAt, readAt)` — em `ComunicacaoDashboardPort.kt`

## Cleanup Scheduler (IAM)

O `IamTokenCleanupScheduler` roda diariamente às 03:00 e purga:
- Refresh tokens expirados da tabela `refresh_token`
- Entradas expiradas da tabela `jti_blacklist` (one-time tokens de reset de senha)

Redis não precisa de cleanup — todas as chaves têm TTL e expiram automaticamente.
